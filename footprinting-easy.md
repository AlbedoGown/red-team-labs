# Footprinting — Easy: NIXEASY (FTP/DNS/SSH chain)

## Задача
Найти файл `flag.txt` на целевой машине, изучив открытые сервисы.

## 1. Recon (Nmap)

```
nmap -A 10.129.141.200
```

Результат:

| Порт | Сервис | Версия |
|------|--------|--------|
| 21/tcp | ftp | ProFTPD (ftp.int.inlanefreight.htb) |
| 22/tcp | ssh | OpenSSH 8.2p1 Ubuntu |
| 53/tcp | domain | ISC BIND 9.16.1 |
| 2121/tcp | ftp | ProFTPD (Ceil's FTP) |

**Почему это важно:** два FTP-сервиса на разных портах и один DNS — сразу два вектора: DNS-разведка и потенциально разный доступ на разных FTP-инстансах (анонимный vs авторизованный).

## 2. DNS zone transfer (AXFR)

DNS-сервер (BIND 9.16.1) разрешил передачу зоны без ограничений:

```
dig AXFR inlanefreight.htb @10.129.85.254
```

Это отдало полный список записей зоны, включая `internal.inlanefreight.htb`.

**Root cause:** отсутствие ACL на AXFR-запросы в конфигурации BIND. По умолчанию BIND должен ограничивать зону такой директивой:

```
zone "inlanefreight.htb" {
    type master;
    allow-transfer { <IP слейв-серверов>; };
};
```

Без `allow-transfer` (или с `allow-transfer { any; }`) любой клиент может скачать всю зону — это классическая ошибка конфигурации, попадающая в категорию **Information Disclosure / Misconfiguration**, а не эксплуатация уязвимости кода.

## 3. Брутфорс поддоменов

Добавили `internal.inlanefreight.htb` в `/etc/hosts` и прогнали `dnsenum`:

```
dnsenum --dnsserver 10.129.85.254 --enum -p 0 -s 0 \
  -f /opt/useful/SecLists/Discovery/DNS/subdomains-top1million-5000.txt \
  internal.inlanefreight.htb
```

Нашли `ftp.internal.inlanefreight.htb` → 127.0.0.1 (внутренний алиас, реально резолвится на тот же хост).

## 4. Второй FTP на порту 2121

```
nmap -T4 ftp.internal.inlanefreight.htb
```

Порт 2121 — тоже ProFTPD, но с другим баннером ("Ceil's FTP"), что намекает на отдельного пользователя.

## 5. Аутентификация и поиск ключа

Используя учётные данные из материалов лабы (`ceil:<PASSWORD_PLACEHOLDER>`):

```
ftp ftp.internal.inlanefreight.htb 2121
ls -al
ls .ssh/
cd .ssh
get id_rsa
```

Нашли приватный SSH-ключ `id_rsa` в `~/.ssh/` — доступный по FTP, потому что права на директорию (`drwx------`) не мешают самому пользователю `ceil` читать свои файлы через FTP-сессию, авторизованную как `ceil`.

**Важный нюанс для размышления:** ключ был доступен НЕ потому что права файлов слабые (там `-rw-------`, то есть 600), а потому что FTP-сессия уже аутентифицирована как владелец файла. Это не уязвимость прав доступа — это следствие того, что мы уже получили валидные credentials на предыдущем шаге.

## 6. Использование ключа

```
chmod 600 id_rsa
ssh -i id_rsa ceil@10.129.85.254
cat /home/flag/flag.txt
```

Флаг: `HTB{FAKE_EASY_FLAG_1234567890abcdef}` *(заменено на нереальное значение)*

## Remediation

- Настроить `allow-transfer` в BIND, разрешив AXFR только доверенным IP (slave-серверам).
- Не хранить приватные SSH-ключи в домашней директории пользователей, доступных через FTP; использовать `chroot` для FTP-пользователей (ProFTPD `DefaultRoot ~`).
- Отключить парольную аутентификацию по FTP там, где возможно, в пользу SFTP/SCP.
- Ограничить видимость скрытых файлов (`.ssh`) даже в рамках домашней директории через ACL FTP-сервера.

## Lessons learned

- AXFR — первый чек при виде открытого 53 порта; это самый "дешёвый" источник инфраструктурной информации (поддомены, внутренние хосты).
- Наличие двух FTP-сервисов на разных портах почти всегда значит "разный контекст доступа" — стоит проверять оба.
- FTP как транспорт для кражи SSH-ключей — типичный lateral movement паттерн: одна слабая точка (FTP creds) даёт доступ ко второй (SSH key).
