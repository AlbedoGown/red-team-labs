# Starting Point: Cap (Easy)

> ⚠️ Все флаги, пароли и хеши в этом write-up заменены на нереальные значения перед публикацией (репозиторий публичный).

## Задача

Цель — получить полный компромисс Linux-хоста Cap (Starting Point, Tier 0) через веб-приложение "Security Dashboard" на Gunicorn, включая этап privilege escalation до root (в отличие от предыдущих машин Responder и Three, где privesc не потребовался).

## Recon

**Nmap-скан** показал три открытых TCP-порта:

```
21/tcp open  ftp     vsftpd 3.0.3
22/tcp open  ssh     OpenSSH 8.2p1 Ubuntu 4ubuntu0.2
80/tcp open  http    Gunicorn — "Security Dashboard"
```

Порядок recon был выстроен так: сначала проверка anonymous-доступа на FTP (стандартный baseline-чек для любого FTP-сервиса), затем — веб-приложение на порту 80.

**FTP anonymous login:**

```
Name (10.10.10.X:user): anonymous
331 Please specify the password.
Password:
530 Login incorrect.
```

Сервер отдал `331` (значит, USER `anonymous` в принципе распознаётся), но и пустой пароль, и `anonymous`/`anonymous` завершились `530 Login incorrect`. Anonymous-доступ на этой машине не сработал — это тупиковая ветка, о чём стоит явно писать в отчёте (проверенная и закрытая гипотеза, а не забытый шаг).

**Веб-приложение (порт 80):** главная страница — форма "Please Enter PCAP to be analyzed" с `POST /upload`. Приложение принимает pcap-файл и, судя по всему, анализирует его, сохраняя результат под инкрементным числовым ID, доступным через `GET /data/<N>`.

Обращение к `/data/0` без какой-либо аутентификации и без единой собственной загрузки файла отдало готовый pcap, принадлежащий другому (легитимному) пользователю дашборда.

## Vulnerability / Misconfig

Цепочка компрометации построена на **трёх независимых недостатках**, каждый из которых сам по себе не был бы критичен, но в комбинации дали полный доступ к системе.

### 1. IDOR (Insecure Direct Object Reference) на `/data/<N>`

Приложение обращается к сохранённым результатам анализа по простому инкрементному числовому ID, без проверки того, что запрашивающий — владелец этого конкретного ресурса. Root cause: на сервере отсутствует авторизация на уровне объекта (в терминологии OWASP API Security Top 10 — **Broken Object Level Authorization**, API1:2023). Аутентификация запроса (если она вообще есть) проверяет только "залогинен ли пользователь", но не "принадлежит ли ему конкретный `data/<N>`".

Файловая система подтвердила это прямо — на диске лежит серия файлов `/var/www/html/upload/0.pcap` … `/var/www/html/upload/7.pcap`, все физически доступные через простой перебор ID в URL.

### 2. Открытая передача credentials по FTP (protocol design flaw)

Один из перехваченных в pcap-файле трафиков содержал полную FTP-сессию:

```
USER nathan
331 Please specify the password.
PASS <REDACTED_PASSWORD>
230 Login successful.
```

Root cause: классический FTP не шифрует управляющий канал — команды `USER`/`PASS` передаются открытым текстом. Это не ошибка конфигурации, а фундаментальное свойство протокола (в отличие от FTPS/SFTP, где канал шифруется TLS/SSH). Любой, кто получает доступ к трафику — будь то живой перехват (MITM, как в случае с Responder-атакой на предыдущей машине) или, как здесь, уже записанный pcap, слитый через отдельную уязвимость — читает креды без каких-либо дополнительных усилий. Сложность самого пароля здесь не имеет значения: канал скомпрометирован целиком, а не подобран брутфорсом.

### 3. Избыточная Linux capability на системном интерпретаторе

На хосте на бинарник `/usr/bin/python3.8` была выставлена file capability `cap_setuid` (обнаруживается через `getcap -r / 2>/dev/null`). Root cause: capabilities — это более гранулярная альтернатива классическому SUID-биту, позволяющая выдать процессу отдельные привилегированные операции без полного root. Проблема в том, что `cap_setuid` был выставлен на **интерпретатор общего назначения**, а не на узкий, специально написанный бинарник под конкретную задачу. Любой пользователь, способный запустить этот Python, получает возможность вызвать `os.setuid(0)` и получить процесс с UID 0, минуя стандартные механизмы разграничения прав (sudo, PAM).

## Exploitation

1. **Baseline recon FTP** — попытка anonymous login, подтверждён отказ (`530`), вектор закрыт.
2. **Веб recon** — обнаружена форма загрузки pcap на порту 80, а также эндпоинт `/data/<N>`.
3. **IDOR-эксплуатация** — запрос `GET /data/0` вернул чужой pcap-файл без аутентификации.
4. **Анализ pcap** — открытие файла в Wireshark, фильтр `ftp`, восстановление FTP-сессии (`Follow → TCP Stream`) выявило plaintext credentials пользователя `nathan`.
5. **Доступ по FTP/SSH под `nathan`** — логин с найденными credentials, получен `user.txt`.
6. **LinPEAS-энумерация** — автоматизированный privesc-recon выявил file capability `cap_setuid` на `/usr/bin/python3.8`.
7. **Privilege escalation:**

```
$ /usr/bin/python3.8
>>> import os
>>> os.setuid(0)
>>> os.system("/bin/bash")
# id
uid=0(root) gid=1001(nathan) groups=1001(nathan)
```

8. **root.txt получен:**

```
root@cap:~# cat /root/root.txt
<REDACTED_ROOT_FLAG>
```

## Remediation

- **Object-level authorization на `/data/<N>`:** каждый запрос к ресурсу должен проверять владельца (`WHERE id = ? AND owner_id = current_user.id`), а не только сам факт наличия ID. Дополнительно — использовать непредсказуемые идентификаторы (UUID) вместо инкрементных чисел, чтобы исключить тривиальный перебор.
- **Замена FTP на защищённый аналог:** для передачи любых credentials или чувствительных данных — SFTP (SSH-based) или FTPS (FTP over TLS) вместо plaintext FTP. Если легаси-FTP всё же необходим — минимум ограничить его сетевым уровнем (внутренний VLAN, VPN, запрет доступа из внешней сети) и не хранить в нём файлы, содержащие живые креды.
- **Аудит file capabilities в системе:** регулярный контроль (`getcap -r / 2>/dev/null` в рамках CI/CD или периодического хостового аудита) на предмет capabilities, выставленных на интерпретаторы общего назначения (python, perl, node, bash, ruby). Если конкретной автоматизации нужна привилегированная операция — выносить её в отдельный узкоспециализированный бинарник/скрипт с минимально необходимым набором capabilities, а не давать capability всему интерпретатору.
- **Мониторинг признаков enumeration-атак:** всплеск последовательных запросов к `/data/0`, `/data/1`, `/data/2`... с одного IP/сессии — классический индикатор перебора ID, который должен триггерить алерт в SIEM/WAF.

## Lessons learned

- Одна "несерьёзная" на первый взгляд уязвимость (IDOR на дашборде для аналитики) стала входной точкой для куда более серьёзной компрометации (утечка живых credentials), потому что на сервере оказался записан реальный чувствительный трафик. Это иллюстрирует, почему даже низко-critical находки в отчёте пентестера нельзя недооценивать — контекст (что именно "утекает") может резко поднять реальный impact.
- Комбинация из нескольких *независимых* слабых мест — не exploit-chain в классическом смысле (не эскалация одной уязвимости в другую), а параллельно существующие ошибки, которые совместно дают полный доступ. Полезный вывод для пентест-отчёта: описывать каждую находку отдельно с собственным risk-рейтингом, но также явно показывать, как они складываются в единый путь атаки (attack path), если это релевантно.
- LinPEAS — быстрый способ автоматизировать recon на privesc, но выдаёт большой объём потенциальных векторов (в том числе множество kernel CVE по одному совпадению версии). Важно уметь отличать сигнатурные совпадения ("possibly vulnerable, если версия ядра ниже X") от подтверждённых, конкретных misconfiguration (как file capability на конкретном бинарнике) — последние почти всегда надёжнее и быстрее в эксплуатации на уровне Starting Point/Easy.
- FTP как протокол — устаревший стандарт, всё ещё встречающийся в реальной инфраструктуре (легаси-системы, внутренние file-share сервисы). Знание, что его управляющий канал plaintext, критично для SOC-анализа сетевого трафика: если в реальном окружении видно живые FTP-сессии с реальными кредами в открытом виде — это finding с High severity независимо от "силы" самого пароля.
